# Phase 0 — working GUI with fake options

Status: **complete**.

Phase 0 carries almost all of Satsuma's looks and behavior: the [design.md](design.md)-styled wedge menu, the full [interaction.md](interaction.md) model, tray-resident background mode, the borderless desktop overlay, and both platforms' file-manager triggers. The *only* thing Phase 0 doesn't have is real conversion/tool engines — format wedges write a stub sibling file (same name, swapped extension, no real transcoding) and advanced-tool wedges are no-ops. See [phases/functionality-phases.md](phases/functionality-phases.md) for how the later phases build on top of this.

## What Phase 0 required

1. A drag-and-drop zone that accepts a file and identifies its type/category (image/video/audio) from its extension — no real conversion yet.
2. The citrus-slice radial menu UI (SVG wedges, hover/selection states, keyboard navigation), styled per [design.md](design.md).
3. Full interaction model wired up per [interaction.md](interaction.md) (Shift to open menu, Alt to switch to tools mode, arrow keys + Enter/Escape) — selecting a format wedge writes a real stub sibling file; selecting a tool just logs/displays the selection.
4. Tray-resident background mode + autostart, and a borderless desktop overlay window for the file-manager trigger paths.
5. Windows and Linux file-manager trigger paths (Windows global Shift-hook + Explorer COM automation; Linux context-menu integration).
6. Test coverage on both sides (frontend: rendering, keyboard nav, drag/drop state, menu behavior; backend: Tauri command scaffolding, file-type detection, stub conversion, platform-integration logic).

## What was built

### Cargo workspace

The Rust side is a workspace (`Cargo.toml` at the repo root) with two members, split deliberately so the conversion/detection engine stays independent of — and testable without — the Tauri command layer:

- **`crates/satsuma-core`** — pure Rust, no Tauri dependency.
  - [`file_type.rs`](../crates/satsuma-core/src/file_type.rs) — `detect_category(path) -> FileCategory` (Image/Video/Audio/Unknown), extension-based, case-insensitive, handles both `/` and `\` path separators and dotfiles correctly.
  - [`launch_request.rs`](../crates/satsuma-core/src/launch_request.rs) — `parse_launch_args` parses `--mode=formats|tools <path>...` out of process arguments, for the file-manager trigger paths below.
  - [`overlay_geometry.rs`](../crates/satsuma-core/src/overlay_geometry.rs) — pure screen-rect placement math (`overlay_position`), kept OS-agnostic so it's testable without a Windows toolchain.
  - `stub_conversion.rs` — collision-safe sibling-file naming for the stub conversion behavior (see below).
- **`src-tauri`** — the Tauri app and its command layer.
  - [`src/lib.rs`](../src-tauri/src/lib.rs) exposes `detect_file_category`, a thin wrapper delegating to `satsuma-core`. Real conversion commands come in [phases/phase-2.md](phases/phase-2.md).

### Frontend (React + TypeScript + Vite)

- [`hooks/useFileDrop.ts`](../src/hooks/useFileDrop.ts) — subscribes to Tauri's native `onDragDropEvent` (not HTML5 drag events, per the architecture requirement), tracks drag-over state, and calls the `detect_file_category` command on drop.
- [`hooks/useModifierKeys.ts`](../src/hooks/useModifierKeys.ts) — tracks live Shift/Alt state via window-level `keydown`/`keyup`, resetting on `blur` so a modifier released while unfocused doesn't get stuck "held."
- [`components/DropZone.tsx`](../src/components/DropZone.tsx) — the drop target; shows the detected category and hints once a file is dropped.
- [`components/WedgeMenu.tsx`](../src/components/WedgeMenu.tsx) — the SVG citrus-slice radial menu. Geometry (`describeWedge`, `wedgeAngles`, `polarToCartesian`) lives in [`lib/wedgeGeometry.ts`](../src/lib/wedgeGeometry.ts) as pure, independently-tested functions. Supports mouse hover/click and full keyboard navigation (arrow keys to move selection, Enter to apply, Escape to cancel), and labels itself accessibly (`role="menu"`, accessible name switches between "Convert to format" / "Advanced tools").
- [`data/wedgeOptions.ts`](../src/data/wedgeOptions.ts) — the **hardcoded/fake** per-category format and tool lists Phase 0 uses. `getWedgeOptions(category, mode, currentExtension)` also filters out the file's current extension from the format list, so it never offers to "convert" a file to the format it's already in.
- [`App.tsx`](../src/App.tsx) — orchestrates all of the above: holding Shift while a file is present opens the menu (Alt at that moment picks tools mode; Alt can still live-toggle the mode while a *modifier-triggered* menu stays open); pressing Enter with a file present opens the menu for keyboard-only use; selecting a format wedge writes a real stub file (see below), selecting a tool wedge just logs/displays the selection.

## Scope pulled in early: file-manager trigger paths

Partway through Phase 0, testing surfaced that a modifier-and-drag flow isn't the only reasonable trigger — selecting a file directly in the file manager and pressing a modifier is a materially different mechanism (system-wide file-manager integration vs. an app window accepting a drop), so it's documented here as an addition to Phase 0 rather than folded silently into "drag-and-drop":

- **Windows** ([`src-tauri/src/windows_integration.rs`](../src-tauri/src/windows_integration.rs)): a global low-level keyboard hook (`WH_KEYBOARD_LL`) watches for Shift while Explorer is the foreground window; on Shift-down it queries Explorer's current selection via `Shell.Application` COM automation (`IShellWindows` → matching `IWebBrowserApp` by HWND → `IShellFolderViewDual` → `SelectedItems`) and brings up the wedge menu already open for those files (Alt held too → tools mode).
- **Linux** ([`src-tauri/src/linux_integration.rs`](../src-tauri/src/linux_integration.rs)): there is no cross-file-manager API for "currently selected file," so this ships as context-menu integration instead — a Nautilus "Scripts" entry, Nemo actions, a KDE Dolphin service menu, and a standard `.desktop` MIME association as the "Open With" fallback for every other file manager. Installable/removable via an opt-in toggle in the UI ([`components/LinuxIntegrationPanel.tsx`](../src/components/LinuxIntegrationPanel.tsx), Linux-only), writing/removing files under the user's XDG data dirs.
- Both paths converge on the same `LaunchRequest` (`{ mode, paths }`) delivered to the frontend via a `take_launch_request` command (claimed once on startup) and a `launch-request` event (for a second file-manager invocation while the app is already running, forwarded through `tauri-plugin-single-instance`) — see [`hooks/useLaunchRequest.ts`](../src/hooks/useLaunchRequest.ts). It's `OverlayApp`, not `App`, that claims the `LaunchRequest` and renders the menu — see the tray/overlay follow-up below.

### A bug this surfaced and fixed

Wiring the launch-request path exposed a real bug: a `useEffect` was live-syncing the wedge-menu mode from the Alt key *whenever the menu was open*, which silently overrode the explicit mode a launch request had just set (e.g. a "Satsuma Tools" context-menu click would flip back to formats mode because Alt wasn't held). Fixed by tracking which mechanism opened the menu (`menuTrigger: "modifier" | "launch" | null`) and only letting Alt live-toggle the mode for the drag-and-drop/modifier-key path. Now that launch requests open a separate window entirely (see below), `App.tsx`'s `menuTrigger` only ever takes `"modifier" | null` — the distinction moved from "which trigger, within one component" to "which component."

## Follow-up: tray-resident background app + borderless overlay window

Testing on real Windows 10 and Linux Mint hardware surfaced two gaps: the Windows Shift-hotkey did nothing unless Satsuma's window was already open, and both trigger paths opened the wedge menu inside the normal titled window instead of as a borderless popup near the selected file. Full design rationale is in [tray-resident-overlay-design.md](tray-resident-overlay-design.md); summary of what changed:

- **Tray-resident + autostart** ([`src-tauri/src/lib.rs`](../src-tauri/src/lib.rs)): a system tray icon (Tauri's built-in `tray-icon` support) with **Show Satsuma** / **Start at Login** (backed by `tauri-plugin-autostart`) / **Quit**. The main window's close button hides it instead of quitting (`WindowEvent::CloseRequested` intercepted), so the process — and the Windows keyboard hook — stays alive in the background. Linux tray icons need `libayatana-appindicator3-dev` (or equivalent) at build time; see the [README](../README.md).
- **Borderless overlay window**: a second window, `"overlay"` (declared in `tauri.conf.json`: undecorated, transparent, always-on-top, skip-taskbar, 480×480, created hidden at startup and reused rather than recreated per trigger). It renders `OverlayApp` ([`src/OverlayApp.tsx`](../src/OverlayApp.tsx)) — the same `WedgeMenu` component, on a transparent background, with no header/DropZone — picked via a `?window=overlay` URL flag that `main.tsx` branches on. Selecting a wedge or cancelling calls the new `hide_overlay` command instead of destroying the window; losing OS focus also auto-hides it, so clicking elsewhere dismisses it like a normal popup.
- **Positioning**: both trigger paths now call `show_overlay` (in `lib.rs`), which centers the overlay on the current cursor position — not the file icon's exact bounding rect, which would need much deeper per-platform COM/D-Bus work for uncertain benefit — via the existing, already-tested `overlay_position` in `overlay_geometry.rs`. Windows gets the cursor via `GetCursorPos` (`windows_integration::cursor_position`); Linux via an X11 `XQueryPointer` query (`linux_integration::cursor_position`, `x11rb`), skipped entirely on a Wayland session (`XDG_SESSION_TYPE=wayland`) since most compositors don't expose a global pointer query to ordinary clients. Either platform falls back to centering on the primary monitor when no cursor position is available.
- **Trigger wiring**: `windows_integration::handle_shift_pressed` and the Linux launch-request paths (fresh-process argv and single-instance-forwarded) all call `show_overlay` instead of showing/focusing the main window. The main window is now created hidden and only shown for a plain launch with no associated file (and not when started via the `--autostart` flag).

### Practical gotchas found during hardening

A few real, non-hypothetical traps surfaced while getting the above solid:

- **A `cargo build --release` binary alone doesn't work.** Bypassing the Tauri CLI (`cargo build --release -p satsuma` directly, rather than `npx tauri build` / `npm run tauri build`) produces a binary that still tries to load `http://localhost:1420` (the configured `devUrl`) instead of embedding the built `dist/` assets, so every window shows a WebKit "Could not connect to localhost" error unless a dev server happens to be running. Not a bug in this repo's code — just an easy trap when testing manually. Use `npx tauri build --no-bundle` (skips packaging installers, still produces a working `target/release/satsuma`) or `npm run tauri build` (full installer bundles) for a real standalone binary.
- **Linux: the installed context-menu integration invoked a stale binary.** `linux_integration.rs`'s templates called the trigger by bare command name (`Exec=satsuma ...` / `exec satsuma ...`), relying on `$PATH` resolving it to the currently-running build. In practice an older `satsuma` earlier on `$PATH` silently won, so "Convert with Satsuma" kept opening old behavior no matter what changed in the current build. Fixed by baking the running executable's absolute path (`std::env::current_exe()`, passed into `install()`) into the generated `.desktop`/`.nemo_action`/script files instead, properly quoted per context. **Anyone who already had the integration installed from before this fix needs to reinstall the app and re-toggle the file-manager-integration checkbox off/on** to regenerate the integration files with the corrected `Exec=` lines.
- **Windows: the keyboard hook did its COM work synchronously, which Windows can silently punish.** `windows_integration.rs`'s `low_level_keyboard_proc` was calling `handle_shift_pressed()` — full `Shell.Application` COM automation, potentially across several Explorer windows — directly inline. `WH_KEYBOARD_LL` callbacks that don't return quickly get silently disabled by Windows, so a single slow COM call could plausibly turn into "Shift stops doing anything at all" for the rest of the session. Fixed by having the hook callback spawn a dedicated thread (`spawn_shift_handler`, with its own `CoInitializeEx`/`CoUninitialize` and an in-flight guard against OS key-repeat piling up redundant COM calls) to do the actual work, so the callback itself returns immediately regardless of COM latency.
- **Windows: the hook was never installed at all, because a second `.setup()` call silently replaced the first.** `run()` (in `lib.rs`) had two separate `builder.setup(...)` calls — one gated for Windows that installed the global Shift hook, and a second, later call for tray-icon/overlay-window/close-to-tray setup. Tauri's `Builder::setup()` is not additive — each call unconditionally replaces whatever was set before — so the second call silently discarded the first, and the hook never ran on Windows at all. Fixed by merging both into one `.setup()` closure.
- **CI's Windows coverage is narrower than it sounds.** `windows-latest` in [`.github/workflows/ci.yml`](../.github/workflows/ci.yml) runs a genuine native build+link+`cargo test --workspace` pass on every push/PR, but the only test it actually exercises inside `windows_integration.rs` is the pure `parse_launch_args` logic — not the COM/hook/tray/autostart behavior itself. That part still needs manual verification on a real machine or VM.

## Follow-up: Citrus visual identity + stub conversion

- **Visual identity** (`src/theme.css`, `src/App.css`, `src/components/WedgeMenu.css`, `src/components/DropZone.css`): the default "Citrus" theme's color/typography/radius/spacing tokens as CSS custom properties, consumed by every component instead of literal hex values (so a future Settings theme picker only has to remap the tokens). Plus Jakarta Sans (UI text) and Nunito (wedge labels only) are bundled locally via `@fontsource/*` — no CDN, keeping the app fully offline. `WedgeMenu.tsx` gained a **hub** (a non-interactive circle showing the source file's own format, via a `hubLabel` prop plumbed from `App.tsx`/`OverlayApp.tsx`), a **live label** pill above the menu that echoes the hovered wedge's action ("Convert to PNG"), and a **modifier-key hint badge** ("⌥ Hold Alt for advanced tools") shown only the first few times per install (tracked via `localStorage`) — see [design.md](design.md).
- **Stub conversion** (`crates/satsuma-core/src/stub_conversion.rs`, the `stub_convert_file` Tauri command in `src-tauri/src/lib.rs`, wired from `App.tsx`/`OverlayApp.tsx` via `src/lib/tauri.ts`'s `stubConvertFile`): selecting a format wedge writes a real sibling file next to the source — same base name, the newly-selected extension, containing a byte-for-byte copy of the source (no real transcoding yet). Naming is collision-safe per [interaction.md](interaction.md)'s rule (`cat.jpg` → `cat.png`, or if that's taken, `cat 2.png`, `cat 3.png`, ...), never overwriting an existing file. In the main window this surfaces as an auto-dismissing success toast or a persistent failure toast (source filename + error detail); the overlay window fires the write and closes immediately. Advanced-tool wedges are untouched by this — they stay fake (selection is only logged/displayed).

## Follow-up: overlay interaction bugs found in real Linux Mint/Nemo use

Real usage on Linux Mint/Cinnamon/Nemo surfaced three overlay-specific bugs, all fixed:

- **Alt did nothing while the overlay was open.** `OverlayApp.tsx` never called `useModifierKeys()` at all — there was no listener for Alt in that window, full stop. Fixed by wiring it up, with logic that only starts live-toggling the mode once Alt is actually pressed/released after the menu opens, so a "Satsuma Tools" context-menu click (which sets tools mode explicitly, with no modifier held) isn't immediately flipped back to formats the instant the effect runs — see `hasSyncedAltOnce` in `OverlayApp.tsx`.
- **Switching windows didn't close the overlay.** The overlay window was configured with `"focus": false` in `tauri.conf.json` — telling the window manager it should never receive real input focus — while `show_overlay()` simultaneously called `.set_focus()` on it and `lib.rs` registered a `WindowEvent::Focused(false)` handler to hide it on blur. Those two things directly contradicted each other: a window that's configured to never take focus can't generate a "lost focus" event either, so the blur-to-hide handler could never fire. Removed `"focus": false` so the window can actually gain and lose focus. This whole `Focused(false)`-based auto-hide approach was later found unreliable on Linux and replaced entirely — see the Mutter/Muffin section below.
- **An overlay could open blank and swallow clicks meant for whatever was behind it.** Two contributing causes, both fixed:
  1. A race: the Rust side showed the overlay window immediately on a launch request, but the frontend only knew what to render after an async `detect_file_category` round-trip — leaving a real window, however brief, that was visible/focused/on-top but rendering nothing. Fixed by computing the file's category Rust-side (a plain extension check, no I/O) and carrying it directly on `LaunchRequest` (`crates/satsuma-core/src/launch_request.rs`), so the frontend never has to wait on a second IPC call before it knows what to render.
  2. A genuinely unsupported file type (category `Unknown`) would leave `wedgeOptions` permanently empty, so `WedgeMenu` renders nothing at all, indefinitely — and since `WedgeMenu`'s own Escape handling only attaches once it has options to render, there was no way to dismiss it either. Fixed on both ends: `show_overlay_for_request` (`src-tauri/src/lib.rs`) now skips showing the overlay entirely for an `Unknown`-category request (matching [interaction.md](interaction.md)'s "unsupported inputs are rejected outright" rule), and `OverlayApp.tsx` also gained its own Escape listener independent of `WedgeMenu`'s, as a second line of defense against ever being stuck with an invisible, click-eating window.

## Follow-up: Linux overlay focus-stealing workaround

Found during real-hardware testing on Linux Mint/Cinnamon (Muffin, the window manager Cinnamon uses) and left as an accepted, documented platform constraint after several genuine fix attempts, not a bug still being chased:

**Symptom:** after a context-menu trigger opens the borderless overlay, keyboard interaction with it (arrow keys, Enter, Escape) can be unresponsive for anywhere from milliseconds to well over a minute. A real mouse click on the overlay always makes it responsive immediately. Once the wedge menu is genuinely focused, everything behaves correctly (keyboard nav, selection, Escape, and a separate `_NET_ACTIVE_WINDOW`-watching mechanism correctly closes it when the user switches to a different window — that part is solid and unaffected by this issue).

**Root cause, established via correlated, timestamped logging on real hardware:** Tauri's windowing layer (`tao`) asks GTK to focus the overlay via `gtk_window_present_with_time(GDK_CURRENT_TIME)` — i.e. no real timestamp. Mutter/Muffin's focus-stealing-prevention treats an unsolicited activation request without a strong, recent, genuine-input-correlated timestamp as low-confidence, and can *defer* honoring it (not flatly reject it) until it separately observes what it considers real user input — a mouse move or click. Timestamped logs showed the exact same, well-formed `_NET_ACTIVE_WINDOW` request sometimes taking effect in single-digit milliseconds and sometimes taking 10–100+ seconds, with the delay ending the instant the user next touched the mouse or keyboard for any reason.

**What was tried, in order, each a genuine attempt and each insufficient on its own or combined:**
1. Sending a properly-timestamped `_NET_ACTIVE_WINDOW` client message directly via raw X11 (the same mechanism `wmctrl -a` uses), obtaining a real server timestamp via the standard "self-inflicted `PropertyNotify`" trick. This made the request no longer flatly ignored, but didn't make it prompt.
2. Removing `tao`'s own competing `set_focus()` call so only one activation attempt fires per trigger (two independent activation requests landing close together for the same window was, separately, observed to sometimes cause a spurious focus-then-immediate-defocus with no user action at all).
3. Synthesizing a zero-displacement `MotionNotify` (via the XTest extension, at the cursor's own current position, so nothing visibly moves) immediately before sending the activation request — an explicit, acknowledged hack attempting to manufacture the "genuine recent input" signal Mutter's heuristic seems to want. Tested on real hardware and still did not reliably make the window respond promptly.

**Current state:** the properly-timestamped activation request (attempt 1) and the XTest nudge (attempt 3) are both still in place as best-effort — they don't hurt, and do help in some cases — but neither is relied upon for correctness. This is treated as an accepted Mutter/Muffin platform constraint, not an open bug. Diagnostic logging for this whole investigation (`show_overlay`, `force_activate_window`, `current_server_time`, the window-event handler, the active-window watcher) is retained in the repo behind a Cargo feature flag (`debug-overlay-focus`, off by default) rather than deleted, so a future investigation doesn't have to rebuild this instrumentation from scratch.

**Confirmed Linux-specific:** manually verified on real Windows hardware that the overlay does not have this focus-acquisition problem there at all — Windows' `set_focus()` path is honored immediately, with no equivalent deferral. None of `force_activate_window`/`nudge_input_activity`/the `_NET_ACTIVE_WINDOW` watcher run on Windows at all (all Linux-only via `#[cfg(target_os = "linux")]`) — it's specifically Mutter/Muffin's own focus-stealing-prevention behavior, not something inherent to the overlay's design.

**Not yet tried / possible future directions:** querying whether Mutter/GNOME expose any per-app or global focus-stealing-prevention leniency setting beyond `org.cinnamon.desktop.wm.preferences focus-new-windows` (checked — a `smart`/`strict` enum specifically about brand-new windows, not an existing window asking to be re-activated, so it doesn't apply here); whether a small delay before sending the activation request changes anything; or accepting the delay and instead surfacing a visible "waiting for focus" state in the overlay UI itself.

## Known gaps / what's not verified

- **Windows integration**: the hook/overlay/COM code path has been verified by manually running the built app in a Windows VM, layered on top of the `windows-latest` CI job described above. What's *not* yet verified end-to-end on real hardware: the tray icon's actual rendering/menu interaction, and the autostart entry surviving a real reboot/login.
- **No pixel-accurate icon positioning.** The overlay centers on the cursor position, not the selected file icon's exact bounding rect — see [tray-resident-overlay-design.md](tray-resident-overlay-design.md) for why that's a deliberate v1 scope call, not an oversight.
- **No global cursor position on Wayland.** `linux_integration::cursor_position` returns `None` on a Wayland session by design (most compositors don't expose a global pointer query to arbitrary clients), so the overlay falls back to monitor-center placement there. X11 sessions (including the Linux Mint/Cinnamon setup this was tested on) get real cursor-based positioning.
- Formats/tools shown in the wedge menu are hardcoded fake data (by design — this is exactly Phase 0's scope), and selecting a format wedge writes a real but **unconverted** sibling file (a byte copy under the new extension, not real transcoding). [phases/phase-2.md](phases/phase-2.md) replaces the byte copy with a real, working conversion engine.
- Broader Linux desktop-environment coverage (GNOME/Nautilus, KDE Dolphin, the generic `.desktop`/"Open With" fallback) beyond the Linux Mint/Nemo setup actually tested day to day — see [phases/linux-desktop-coverage-hardening.md](phases/linux-desktop-coverage-hardening.md).
