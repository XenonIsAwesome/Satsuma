# Third-party licenses

Satsuma's own code and assets are MIT-licensed (see [LICENSE](LICENSE)). This
file lists the third-party software distributed with Satsuma — statically
linked Rust crates, bundled npm/frontend packages, and two vendored native
components — and the license each one ships under.

The curated sections below (direct dependencies, the unrar/ffmpeg/pdfium
writeups) are maintained by hand against `Cargo.toml` (root,
`crates/satsuma-core`, `src-tauri`) and `package.json`. The two appendices
at the end — marked `AUTOGENERATED` — are generated by
[`scripts/update-third-party-licenses.mjs`](scripts/update-third-party-licenses.mjs);
run `node scripts/update-third-party-licenses.mjs` to refresh them whenever
a dependency is added/removed or a version bump changes its declared
license, and before cutting a release. Never hand-edit the text between an
`AUTOGENERATED` marker pair — the next run overwrites it.

## How license compliance is enforced

The full transitive Rust dependency tree (covering every target Satsuma
ships for — `x86_64-unknown-linux-gnu`, `x86_64-pc-windows-msvc`,
`x86_64-pc-windows-gnu` — see the exact count in the appendix below) is
restricted by [`deny.toml`](deny.toml)'s `[licenses]` allow-list, enforced in CI via
`cargo deny check licenses`. Every crate in that tree resolves to one of:
MIT, Apache-2.0 (with or without the LLVM exception), BSD-2-Clause,
BSD-3-Clause, ISC, Zlib, Unicode-3.0, CC0-1.0, 0BSD, MIT-0, Unlicense, or
MPL-2.0 (file-level only, in a handful of `tao`/`wry` webview transitive
deps — doesn't require Satsuma's own code to be MPL). See the "Full Rust
dependency tree" appendix below for the actual crate list.

**Caveat:** `cargo-deny`'s license check reads each crate's *own* declared
`license` field. It cannot see license terms of vendored/bundled non-Rust
source *inside* a crate's build — which is exactly the situation with
`unrar` below. That one was audited by hand, not by tooling.

## Special-attention dependencies

### unrar — RAR reading

Reading RAR archives (`crates/satsuma-core/src/convert/archive.rs`) uses the
`unrar` crate (v0.5.8). The **Rust binding code itself** is dual MIT/Apache-2.0
(confirmed via `cargo metadata`) — but that binding compiles and links
RARLAB's own official UnRAR C++ source (`unrar_sys`'s vendored `vendor/unrar`
tree), which ships under **RARLAB's own license, not MIT/Apache/BSD**:

> UnRAR source code may be used in any software to handle RAR archives
> without limitations free of charge, but cannot be used to develop RAR
> (WinRAR) compatible archiver and to re-create RAR compression algorithm,
> which is proprietary. Distribution of modified UnRAR source code in
> separate form or as a part of other software is permitted, provided that
> full text of this paragraph, starting from "UnRAR source code" words, is
> included in license, or in documentation if license is not available, and
> in source code comments of resulting package.

This paragraph is reproduced verbatim above per the license's own
requirement, and again in `crates/satsuma-core/src/convert/archive.rs`'s
module doc comment (the "in source code comments of resulting package"
clause).

**cargo-deny does not catch this.** `cargo metadata`/`cargo-deny` only see
the `unrar`/`unrar_sys` crates' own declared `MIT OR Apache-2.0` license —
that's accurate for the Rust wrapper code, but has no visibility into the
non-Rust source those crates compile in. `cargo deny check licenses` passing
is not, by itself, evidence this dependency is clear.

Usage stays strictly within the license's "read/extract, never re-implement
RAR compression" grant — Satsuma's RAR *writer* is an independent,
from-scratch RAR5 (store-method only) implementation sharing no code with
UnRAR. That said:

- This is not an OSI-approved or MIT/Apache/BSD-compatible license.
- It's bundled as compiled-in C++ **source**, not linked as a system
  library the user already has installed.
- Debian ships `unrar` in `non-free` specifically because of this license's
  wording — it's an unusually-worded grant, not a standard permissive one.

**Decision (project owner, 2026-09-21): ship with RAR support as-is.** The
license's own text ("may be used in any software to handle RAR archives
without limitations free of charge") explicitly covers exactly what Satsuma
does — read-only, no re-implementation of RAR compression, required
disclosure paragraph reproduced above and in `archive.rs`. The direct-
violation risk is low; the real cost is that Satsuma isn't a strictly
permissively-licensed project while this is compiled in (the Debian
`non-free` classification above is the concrete, precedented consequence —
not a licensing-fee or enforcement risk). That tradeoff has been weighed
and accepted in favor of keeping RAR support. Revisit if that calculus
changes (e.g. a permissively-licensed RAR reader ever becomes available, or
distro packaging becomes a priority) — see the options below, still valid
if so.

Options if that decision ever needs revisiting:
- Drop RAR read support entirely (no permissively-licensed Rust crate reads
  RAR — you'd be removing the format, not swapping implementations).
- Gate RAR reading behind a separate, clearly-labeled optional
  build/download (keeps the default build free of RARLAB's license terms).

### ffmpeg — GPL-3.0 sidecar, deliberate, not accidental

`scripts/fetch-ffmpeg.sh`/`.ps1` pull BtbN's **"gpl" build variant**
(confirmed by running the fetched binary: `ffmpeg -version` reports
`--enable-gpl --enable-version3 --enable-libx264 --enable-libx265`), needed
for H.264/HEVC encoding in the video family
(`crates/satsuma-core/src/convert/video.rs`). This is **not** an
LGPL-only build — libx264/libx265 are GPL-licensed codec libraries, and
FFmpeg only enables them under `--enable-gpl`.

This is already called out in both fetch scripts' own comments and doesn't
change Satsuma's own required license, for the same reason many commercial
and open-source apps bundle a GPL FFmpeg build alongside differently-licensed
code: FFmpeg is invoked as a **separate subprocess** (spawned with
command-line arguments, communicating over stdio/exit-code — see
`ffmpeg.rs`), never linked into Satsuma's own binary or sharing an address
space with it. This is "mere aggregation" under the FSF's own GPL FAQ
guidance, not a combined/derivative work — the same reasoning that lets
apps ship a bundled `ffmpeg` binary without themselves becoming GPL.

Compliance requirements this still imposes, both already met:
- **License text must be distributed alongside the binary** — `COPYING`
  (GPL-3.0 full text) is fetched into `src-tauri/lib/ffmpeg/` and mapped
  into the installer's resource directory by `tauri.conf.json`.
- **Source availability** — satisfied by FFmpeg's own upstream project and
  BtbN's public build scripts/CI; Satsuma doesn't need to host a mirror
  since it isn't modifying FFmpeg's source.

**Flagging per your instructions, not silently deciding:** if you'd rather
ship a non-GPL-encumbered sidecar, `fetch-ffmpeg.sh`/`.ps1` can pull the
"lgpl" build variant instead — at the cost of losing libx264/libx265
(H.264/HEVC) encoding, which the video format matrix currently depends on.
That's a real feature trade-off, not a drop-in swap, so it's your call.

### pdfium — clean

BSD-3-Clause (bblanchon/pdfium-binaries, itself repackaging Google's
Chromium-derived pdfium under the same license). Permissive, no attribution
gymnastics beyond "keep the license text around," which is already
satisfied: `LICENSE-BSD3.txt` is fetched into `src-tauri/lib/pdfium/` and
mapped into the installer's resource directory the same way as FFmpeg's
`COPYING`. No action needed.
